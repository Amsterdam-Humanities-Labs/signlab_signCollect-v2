System overview

02 · the whole machine on one map
SignCollect menu_beta is a single-page app (no framework, vanilla JS modules) talking JSON to a flat-file PHP REST layer. All gloss data lives in MySQL database admin_gebarenoverleg. Glosses can be linked to Global Signbank (signbank.cls.ru.nl); once linked, edits and video uploads auto-propagate. Satellite tools at the site root share the same database and session cookie.

Menu & tool ecosystem

03 · every entry in the nav drawer
The hamburger menu in index.html is the hub of the SignCollect suite. menu_beta itself is the gloss list/editor; the other entries link to standalone tools at the signcollect.nl root that share the database and the sessionObject cookie.

Core — this app

Gloss list & editor (menu_beta)

/menu_beta/index.html — search, filter, paginate glosses; inline editing, senses, labels, phonology, notes, logbook, video recording, Signbank sync. Backend: php_api/ + signbank_sync/ → form_data / lsm_data.

Manage section

Batch toevoegen — batch glosses

/batch_add.html → batch_add.php. Paste a word list; parses it and INSERTs new glosses into form_data (optionally linking Signbank IDs and merging labels into existing rows).

Labels toevoegen — label manager

/labels_add.html → labels_add.php. Create / rename / recolour / delete labels in the labels table; renames cascade into the form_data.labels JSON arrays.

Themas aanpassen — theme editor

/themas.html → themas_change.php. Renames a thema category by UPDATE-ing every matching form_data.thema value.

Admin & stats (role-gated)

Account

Login / logout

/login.html → login_sc.php validates against users and sets the sessionObject cookie. Both logout buttons route through /logout.html (confirmation + cookie clear).

Orientation tip: if a tool is reachable from the menu but is not under /web/menu_beta/, it is a site-root tool with its own PHP backend — but it still reads/writes the same MySQL tables, so changes there appear in menu_beta immediately.

Frontend modules

04 · /menu_beta/js — vanilla ES modules, no framework
index.html contains all markup (filter bar, list container, every modal); the JS modules wire it up. State (active dataset, context, filters, page) lives in main.js. Every server call goes through api.js, the single fetch wrapper that attaches the dataset parameter and handles 401 → login redirect.

main.js — orchestrator

Boot sequence, global state, filter bar listeners (search debounce 300 ms), pagination, all modal controllers (add, record, notes, logbook, Signbank broadcast/compare), dataset & context switching, nav drawer.

api.js — API client

One function per endpoint (list, create, save, uploadVideo, notesList, broadcastToSignbank, …). JSON POST/GET with credentials:'same-origin'; central error → toast handling.

table.js — row renderer

Renders each gloss row: thumbnail column (lazy video previews, FIFO queue, max 4 concurrent loads), main column (gloss + senses inline editors), meta column (labels / thema / owner pills), actions column (record, notes, logbook, phonology, Signbank buttons).

recorder.js — VideoRecorder

Wraps getUserMedia + MediaRecorder; captures WebM (VP9/VP8) blobs for the zelfopname upload pipeline (page 10).

phonology.js — phonology editor

Modal with 19 fields: 14 dropdowns + 5 free-text, options loaded from data/phonology_options.json. Every change auto-saves through glosses_save.php (machine_value stored locally, human label pushed to Signbank).

senses.js / sensesPair.js

Editors for the senses / sensesEngels JSON arrays — add/remove/reorder sense rows, side-by-side NL↔EN pairing.

labelEditor.js

Inline label picker with colour pills; can create a new dataset-scoped label on the fly via labels_create.php.

i18n.js & util.js

i18n.js: NL/EN UI strings keyed by the user's lang preference. util.js: DOM helpers, debounce, toasts.

css/

theme.css layout & nav · filters.css filter bar · table.css rows & thumbnails · modals.css dialogs · video.css players.

Boot sequence

Convention: after any mutation the frontend either re-renders the single row from the snapshot returned by glosses_save.php, or calls refresh() to re-run glosses_list.php with the current filter state.

Database map

06 · MySQL — admin_gebarenoverleg
One row in form_data (NGT) or lsm_data (LSM, identical structure) is a gloss. Multi-value fields are JSON arrays in TEXT columns — there are no foreign-key constraints; relations below are by convention. The logboek column is an append-only audit trail ([YYYY-MM-DD HH:MM]-prefixed lines).

Workflow — boot, list & filter

07 · the read path everything else builds on
On load the SPA fetches the user profile and filter options, then every filter interaction funnels into one call: glosses_list.php. The response rows already include joined video metadata, the thumbnail choice, and duplicate-gloss warnings.

Workflow — adding glosses

08 · single (menu_beta modal) and batch (site-root tool)

Single gloss — “Nieuwe glos” modal

Batch glosses — batch_add.html

Flow

1. User pastes a word list into the textarea at /batch_add.html and picks thema / labels / optional Signbank IDs.
2. The page parses the list client-side and POSTs to batch_add.php.
3. PHP INSERTs a form_data row per new word; for words that already exist it merges labels into the existing JSON array instead of duplicating.

Defaults on insert (both paths)

glosZichtbaar = 0 (visible) · extern = '1' when created in Signio context, NULL for Signbank context · wie = [creatorUserId] · logboek gets a creation entry with timestamp + username.

Duplicate guard: glosses_list.php returns a duplicates array per row (other glosses with the same name), which table.js renders as a warning — batch adds are the most common source of these.

Workflow — editing & Signbank auto-sync

09 · one save endpoint behind every editor
All editors — inline gloss/senses/labels/thema, and every field of the phonology modal — call the same endpoint: glosses_save.php. It diffs old vs new, writes the audit trail, and transparently mirrors the change to Signbank when the gloss is linked (form_data.signbank holds a glossid).

Workflow — video recording (zelfopname)

10 · camera → content-addressed storage → optional Signbank push
Self-recordings are captured in the browser and stored content-addressed: the file name is the SHA-256 of the blob, which makes re-uploads of identical videos naturally idempotent. Studio recordings follow a separate path (the studio pipeline writes matched_transcriptions; menu_beta only reads and soft-deletes those).

Workflow — Signbank lifecycle

11 · broadcast · compare · force push / pull · disconnect

Broadcast — linking a gloss to Signbank

Once linked — the other operations

Compare (fetch_gloss.php)

GETs get_gloss_data from Signbank, builds a side-by-side field diff against the local row, and offers three resolutions in the modal: push the diff, force push, or force pull.

Force push / force pull

force_push.php overwrites Signbank with local values (optionally only selected fields). force_pull.php overwrites the local row with Signbank's version. Both log to logboek.

Auto-sync (passive)

Not a button: every glosses_save.php and upload_video.php on a linked gloss pushes the changed fields only — see pages 09–10.

Disconnect (delete_gloss.php)

NULLs form_data.signbank. The gloss stays on Signbank; only the link is severed, so auto-sync stops.

Field translation happens in sync_helpers.php: local column names map to Signbank field names (glos → “Annotation ID Gloss (Dutch)”), and phonology machine_values (e.g. "2") are translated to human labels via data/phonology_options.json before pushing.

Configuration

signbank_sync/config.php (gitignored; see config.example.php): base_url, api_key, auth scheme (Bearer or X-API-Key), timeout. Dataset mapping: NGT → Signbank dataset 2, LSM → dataset 3.

Auth, sessions & datasets

12 · who may see and edit what

Session model

sessionObject cookie

Login at /login.html → login_sc.php validates against users and sets a JSON cookie: {userId, username, role, expiresAt}. All fetches send it (credentials:'same-origin').

require_session()

Every endpoint starts with this guard (php_api/session.php). Missing/expired cookie → 401, and api.js redirects to /login.html?redirect=<current page>. Logout routes through /logout.html (confirm + clear cookie).

Role-gated UI

  • admin — sees “Gebruikers beheren” (users.html) in the drawer.
  • gomer (hardcoded) — sees the “Statistieken” section.
  • everyone else — Main + Manage + Account sections only.

require_dataset()

Each request names its dataset; the guard checks it against users.allowed_datasets (JSON array) → 403 if not permitted. This is what keeps LSM-only users out of NGT data. The resolved entry supplies the table name and Signbank IDs to all downstream code.

Switchers in the header

Dataset switcher (NGT ↔ LSM): swaps state.dataset; every subsequent request carries it. Context toggle (Signio ↔ Signbank, NGT only): filters on extern='1' vs extern IS NULL.

Request lifecycle (every API call)

Where to start reading code: boot & state → js/main.js · any save behaviour → php_api/glosses_save.php · Signbank field mapping → signbank_sync/sync_helpers.php · access control → php_api/session.php + datasets.php.
